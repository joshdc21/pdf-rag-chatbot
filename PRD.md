# Product Requirement Document (PRD): Streamlit UI for PDF RAG Assistant

## 1. Project Overview
The goal is to build a web-based frontend application (`app.py`) using **Streamlit**. This frontend will serve as the user interface layer for the existing backend module (`pdf_reader.py`). The application will allow users to upload PDF documents via a web browser, automatically parse and index them into an existing local ChromaDB vector database, and provide a polished chat interface to query the documents using Retrieval-Augmented Generation (RAG).

## 2. Codebase Integration & Architecture
To keep the codebase modular, the frontend application must comply with the following architectural rules:
* **Separation of Concerns:** Do not duplicate backend mechanics (text splitting, database query structure, Gemini prompt generation) in `app.py`. 
* **Direct Component Imports:** Import existing clients, instances, and helper functions directly from `pdf_reader.py`:
  ```python
  from pdf_reader import (
      client, collection, splitter, hash_content,
      retrieve_documents, rewrite_query_with_history
  )
  ```
* **Adapt Ingestion for Memory Buffers:** The original `ingest_documents()` function reads paths from a local folder via `glob`. The frontend must implement an altered version of this loop that handles Streamlit's in-memory stream buffers (`UploadedFile` objects) generated by the UI upload component.

## 3. UI Layout & Visual Specifications
The interface must follow a classic, responsive **split-screen layout**:

### A. Sidebar (Document Management & Configuration)
* **Header:** A clean section title (e.g., `Documents`).
* **File Uploader:** An `st.sidebar.file_uploader` instance configured for multiple files (`accept_multiple_files=True`) accepting only `.pdf` formats.
* **Process Button:** A clear action button labeled "Process & Index PDFs".
* **Status Area:** A text/visual area beneath the button using `st.spinner()` during ingestion. It should print clean status messages for each file processed (e.g., "Processing...", "Skipping... already processed", "Added to ChromaDB").

### B. Main Application Window (Chat Interface)
* **Application Header:** A prominent workspace title (e.g., `PDF Chatbot Assistant`).
* **Chat Message Feed:** A scrollable message history element utilizing Streamlit's native containers (`st.chat_message("user")` and `st.chat_message("assistant")`).
* **Input Box:** A sticky bottom prompt entry component using `st.chat_input()`.

## 4. State Management Requirements (`st.session_state`)
Because Streamlit re-runs the entire Python script on every user interaction, data persistence must be explicitly handled. Initialize and track these session states:
* `st.session_state.messages`: A list of dictionaries `{"role": "user" | "assistant", "content": str}` to persist and display past conversations on screen.
* `st.session_state.conversation_history`: A list matching the exact structure required by the backend's `rewrite_query_with_history()` context function.

## 5. End-to-End Application Workflow

### Step 1: File Ingestion Flow
When the user clicks the "Process & Index PDFs" button:
1. Loop through all files loaded into the file uploader wrapper.
2. For each file, pass the object directly into the backend reader: `reader = PdfReader(uploaded_file)`.
3. Extract text page-by-page, recording the page indices sequentially.
4. Calculate the text's SHA256 signature using the imported `hash_content()`.
5. Query the persistent ChromaDB collection using the filename (`uploaded_file.name`) as a metadata filter to check if it has already been indexed.
6. **Deduplication Logic:** 
   * If the file exists and the hash matches, skip processing and print a message to the sidebar status area.
   * If the file exists but the hash differs, delete old chunks from the collection (`collection.delete(where={"source": filename})`) and re-process.
7. Use the imported `splitter.split_text()` to chunk text data, prepare accurate page/source metadata, and commit the arrays to the database via `collection.add()`.

### Step 2: Query & RAG Execution Flow
When a user submits text into the `st.chat_input()` block:
1. Append the user's message to `st.session_state.messages` and instantly render it to the chat view.
2. Call `rewrite_query_with_history()` passing the current user text and `st.session_state.conversation_history`.
3. Take the resulting standalone search query and run it against the database using `retrieve_documents(standalone_query, n_results=5)`.
4. Parse the collection results into a single context string (`retrieved_context`), preserving exact `Source` and `Page` metadata details.
5. Inject this context alongside the user's original message into the system prompt template (exactly as written in the backend script).
6. Send the prompt payload to the `gemini-2.5-flash` model. 
7. Stream or print the final assistant output directly to the window inside an assistant chat bubble.
8. Append both the user prompt and final assistant response to both `st.session_state.messages` and `st.session_state.conversation_history`.

## 6. Non-Functional & Edge Cases
* **Missing API Key:** If the `GEMINI_API_KEY` environmental variable is not set up, intercept execution. Disable the input field and display a warning toast or message banner alerting the user.
* **Empty Collection Safeguard:** If no documents have been parsed or exist inside the local database footprint (`./chroma_db`), render a call-out alert in the chat feed telling the user to upload a file to begin.
* **Graceful Refreshes:** Standard browser refreshes or UI toggles must never drop or wipe out the persistence configuration of the local vector engine database connection.
